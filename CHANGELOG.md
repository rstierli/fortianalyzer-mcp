# Changelog

All notable changes to FortiAnalyzer MCP Server will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **A v2 token envelope with authenticated tags, a shape gate and a deprecation window (#115, works #40).** Tokens now take the form `<marker>-<kid>-<ct>-<tag>` with markers `ip4 ip6 mac sn url host user`, the tag being 32 bits over the type, key id and payload. What the tag buys is forgery refusal: a token whose tag does not verify is refused rather than decrypted, where v1 has no integrity at all and so decrypts a stale, rotated or foreign token to a plausible wrong value that nothing catches. Ordering is the whole of the gate. A v2 hostname token also starts with `host-`, so a shape check placed after the prefix dispatch would never run and the v1 path would take the token first; worse, a v2 token with a flipped tag is a byte-valid v1 token, because the tag is hex and a hyphen and both sit inside the v1 alphabet, so v1 would decrypt it happily to garbage. `unmask_token` therefore asks the shape question before anything else, and anything v2-shaped is committed to v2 whatever v2 then says about it, because a fallback would hand a forger exactly the decrypt the gate exists to refuse. `ArgUnmasker` inherits this by delegating, and a test asserts the delegation rather than trusting it to stay one line. `serial` becomes its own type, and the IPv6 and MAC forms carry colon-free hex payloads. `FAZ_MASKING_ACCEPT_V1_TOKENS` (default `true`) is the deprecation window; **domain and `email_local` are deliberately outside it**, since they are suffix-marked and have no v2 envelope by decision, so their suffix form is not a legacy encoding awaiting retirement but the only encoding they have ever had.

- **The composed skill bundles carry a masking contract test of their own (#129, works #44).** Composition creates a surface the individual tools do not have: `incident_summary` alone draws on five appliance fetch families (`get_incident`, the incident's attached alerts, `get_alerts`, `get_alert_logs` and a `top-threats` FortiView), so a value covered under one tool's spelling can arrive under another's. Every string-bearing field across all 16 skills is enumerated and asserted, 124 field slots over 39 distinct names, by walking the output models rather than by listing them. **No new leak was found.** Two candidates raised from model annotations turned out never to occur in handler output, which is the method note worth keeping: an annotation says a shape is possible, only the handler says whether it ever happens. The finding is a property rather than a bug, and it is now pinned: a bare `value` is covered by context rather than by name, so it is safe only while `type` remains required on both indicator models, an invariant nothing had been holding. `Hash` is deliberately left readable, since it identifies a file and a tokenised hash matches nothing in any feed.

### Fixed
- **SOAR indicator-detail masking no longer burns descriptive threat-intel classification fields (#144).** Live-verified against a real `enrichment_uuid` response (see ADR-0004's #133 update): `_burn_values_and_record`'s enclosing-key fallback, added for #133/#137 to fail closed on a detail provider's own unrecognised nested vocabulary, burned FortiGuard-CTS's own descriptive classification of an indicator (`wf_cate`, `ioc_cate`, `ioc_tags`, `confidence`, `kill_chain_phases`, `created`, `modified`, `malware_name`, `av_cate`, `spam_cates`) alongside the actual identifying value — data that names nobody, identical for every caller who looks the same indicator up. Those keys now pass through unchanged when reachable only under `enrichment-detail`; the identifying value and any URL that embeds it still burn.
- **A group-by map no longer rides through the allowlist walk (#116, closes #73 item 1 in part).** Measured on `cfc2585` with RFC 5737 values before anything was written: `{"groupby1": {"a": "srcip:192.0.2.90"}}`, `{"groupby1": {"a": "192.0.2.90"}}` and `{"groupby1": [{"a": "srcip:192.0.2.90"}]}` all passed the identifier through verbatim, and `{"groupby1": {"192.0.2.90": 5}}` handed it over in the key, because the allowlist walk never masks a key. `_mask_composite_map` now masks an inner key the schema knows and burns everything else, the key included. Half of what #73 listed had already closed since it was filed, so the issue was trimmed against measurement rather than carried: list-shaped group-bys, list-shaped `http_url`, a dict under a URL key failing closed, and `{"groupby1": 12345}` passing through because an int carries no maskable string.
- **A composite container now keeps its key context (#117, closes the rest of #73 item 1).** Rather than take #116 at face value, every composite key was run against every shape under both settings of `FAZ_MASK_DEVICE_IDENTITY`, and the matrix is where the rest was: the map form of two kinds, the key side of a map, and one level deeper in the list arms of all four. `{"devvds": {"a": "fw-oslo-01[root]"}}`, `{"devvds": [["fw-oslo-01[root]"]]}`, `{"http_url": [["https://bad.example.com/x"]]}` and their siblings all leaked verbatim. The container now re-enters `_mask_entry` under the same key for every element, at any depth. **Recursion rather than burning is load-bearing**, because `_mask_device_vdom` self-gates on the identity flag and `_burn_strings` does not, so burning would have masked estate identity the flag says to leave readable.
- **Four of the five leaks the live #80 sweep confirmed (#118).** Every one had the same shape, which is the finding that outlives any single key: the masker covers one spelling of an identifier while the appliance ships a second spelling of the same value on the same surface, usually in the same record. FPE is deterministic, so a record carrying both publishes the token and the plaintext together and hands over the mapping. `f_user` gained a `USERNAME` entry to match its `unauthuser`/`user`/`dstuser` twins; `auto_raise_grpby` joined `COMPOSITE_JSON` to match `grpby`; `mac_devtype_agg` and `dev_src_agg` got a new `COMPOSITE_ID_DEVTYPE` handler that masks the head by the key's type and passes the tail through `mask_text`, matching their `mac`/`stamac` and `hostname`/`srcname` twins. The fifth, a domain in free text, stays blocked on the #40 ruling.
- **The #80 second-tier keys whose fix is a table entry (#119).** Each was re-measured at `0d17c41` before being touched, **and re-measuring is what found that two rows of the published table were wrong**, one of them published by us: `name` on `list_devices` and `devid` on a vdom object both mask flag-on, and had been read as leaks only because the sweep ran with `FAZ_MASK_DEVICE_IDENTITY` off, where estate identity is clear by design. Both are now pinned as correct, as is the counterpart that a bare `{"name": ...}` is not burned, since without a device-proving sibling it belongs to an ADOM, a report layout or a device group. That is the sweep's own method warning one level up: the first form was that a badly sorted surface looks clean, and this one is that a flag-off run makes correct behaviour look like a leak. `COMPOSITE_SOURCE` is gated on the **element** type, not the key name, because live measurement found 152 of 394 endpoint records carry `source` as an array of detection-method labels rather than identifiers, and routing every list to the target handler burned all of them.
- **Identifiers inside percent-encoded free text (#120, the `msg` row of #80).** FortiAnalyzer returns `msg` percent-encoded, so a MAC reached the pass-2 scan as `aa%3Abb%3Acc%3Add%3Aee%3A11` and an email as `analyst%40example.com`, and both regexes need the literal separator, so neither matched. Measured live during the sweep, on 3 of 3 event records the MAC inside `msg` differed from the masked MAC in the structured field of the same record, so the original was recoverable by anyone holding both; one record settled that they really were the same device, its `msg` decoding to `AP <mac> chan 153 live 7235442` while the record's own `channel` and `live` fields matched exactly. The second look lives in `_mask_scalar_text`, the single chokepoint for every TEXT key. **Decoding is a means of finding identifiers, not a reformatting of tool output**, and each consequence is pinned: plain text is scanned exactly as before and never decoded, a scan that already masked something returns that result with no decode at all, and a decode that surfaces nothing to mask returns the exact bytes FortiAnalyzer sent.
- **12 more identifier-bearing groupby dimension names now mint the same token as their flat-field twin (#124, works #80).** `attackerip`, `victimip`, `user_name`, `mail_from` and eight others were untyped, so a composite groupby leaked the identifier under one spelling while the flat field masked the same value under its covered spelling. `logdev_name` leaked in both masking-flag states; the other eleven only with `FAZ_MASK_DEVICE_IDENTITY` off.
- **A stock appliance's certificate cannot pass the verification the old warning recommended enabling (#127, closes #126).** Mirrors the FortiManager-side fix (rstierli/fortimanager-mcp#90): the certificate is self-signed with no SAN, so the warning was pointing operators at a step that cannot succeed, and it named a setting (`FORTIANALYZER_VERIFY_SSL`-adjacent CA bundle) that did not exist in `utils/config.py` at all. A new `FORTIANALYZER_CA_BUNDLE` reaches all three call sites that read `verify_ssl`, including a raw PCAP-download request that read it directly and would otherwise have kept using the old bool while everything else honoured the bundle.
- **Masking a response with many distinct identifiers was quadratic in time, not memory (#128, works #73 item 7c).** The substitution pattern was rebuilt and recompiled from scratch for every TEXT field in a response. Caching it once per response instead took 10,000 distinct identifiers from not finishing in 120 seconds to about 2.

## [2.13.0] - 2026-08-09

Minor release: the output masker now honours the keep set on every pass-1 route, and the server runs on the mcp 2.0 API with the `<2` pin lifted.

### Fixed
- **Keep set honoured on every pass-1 route (#113, closes #73 item 5).** With `FAZ_MASK_DEVICE_IDENTITY` off, a device-identity value stays readable under every key, so a response never shows a token beside the cleartext it stands for. That guarantee was enforced on one pass-1 route plus pass 2; the other routes bypassed it, and a name that appeared under `devname` could still tokenise two keys away. The check now lives in `_mask_scalar`, which every pass-1 route reaches, and folds case for every type except usernames: the engine normalises case before encrypting, so two spellings of a hostname are one identity, whereas usernames are not folded and two spellings are two principals. `keep` is now a required keyword argument, so omitting it on a new route is a type error rather than a silent leak.

### Changed
- **Ported to the mcp 2.0 `MCPServer` API; the `<2` pin is lifted to `>=2,<3` (#114).** The read-only tool-annotation gate now reads `read_only_hint`, the 2.0 field name, alongside the older `readOnlyHint` that a 1.x-only read would have taken as false on 2.0. The wire format stays camelCase and the HTTP mount path is unchanged, so clients see no difference.

## [2.12.0] - 2026-08-06

Minor release, breaking change to the tool surface: honest server-side aggregation on `query_logs` (`group_by`, `sample_by`, `count_only`) and a thirteen-tool consolidation into three (85 → 73) now that every removed tool's parameters are expressible on its replacement.

### Added
- **Projection (`fields`) on every read tool.** `query_logs`, `fetch_more_logs`, `get_alerts`, `get_alert_logs`, `get_incidents`, `get_endpoints`, `get_endusers`, `get_fortiview_data`, `get_report_history` and `search_devices` take `fields: list[str] | None`. Omitting it returns a **curated** subset for that vocabulary; `fields=["*"]` returns the full object exactly as before; an explicit list returns those keys, with the same English aliases the filter surface accepts. A traffic row is roughly sixty keys and a typical answer needs eight, and the cost this addresses is context rather than bandwidth — the appliance offers no server-side projection for logs, alerts, incidents or FortiView rows, so those are trimmed in-process, while `list_adoms`/`list_devices`/`search_devices` forward the list to dvmdb where it is native and the untrimmed object never crosses the wire. Every response gains `fields_returned`, reported even for a zero-row page, since that is exactly when a caller has nothing else to tell it what is queryable next. Two invariants keep the other layers correct: projection **selects, never renames** (the masking allowlist is keyed on live field names, so a rename would move a value out from under its entry and silently unmask it, whereas a subset can only shrink what masking must cover), and it selects **top-level keys only** (a nested `subject_details` or `target[]` survives whole, rather than introducing a second dotted-path query dialect over structures masking handles specially). **Curation is explicit and its absence is never silent truncation:** a vocabulary with no verified field catalogue — uncommon logtypes, and every FortiView view, whose per-view columns remain an unverified item — returns full rows plus a warning naming `fields`, which is precisely today's behaviour. A parametrised test asserts each of 21 cross-tool join keys (`sessionid`, `pcapurl`, `policyid`, `alertid`, `epid`, `euid` and the rest) survives the projection of the tool that produces it, because curating one away would break a workflow with no error that traces back to the projection.
- **Honest aggregation on `query_logs`: `group_by`, `sample_by` and `count_only`.** Three mutually exclusive parameters whose names carry the guarantee. `group_by="<dim>"` dispatches to the surface FortiAnalyzer aggregated itself — a FortiView view — and reports `is_exact: true` because the appliance counted every row. Each view aggregates its own log source, so the mapping is **logtype-scoped**: `logtype="traffic"` serves `srcip`→`top-sources`, `dstip`→`top-destinations`, `policyid`→`policy-hits`, `dstcountry`→`top-countries`; `logtype="webfilter"` serves `catdesc` (alias `web_category`)→`top-websites`; `logtype="attack"` serves `attack`/`threat`→`top-threats`. Requesting a dimension for a logtype its view does not serve is `group_dimension_logtype_mismatch` — dispatching it anyway would return exact counts over a population the caller did not ask about, which is the one failure an exactness promise cannot survive. (The `serves` sets are the conservative reading of each view's documented purpose, not probe results; being wrong costs a refusal, never a wrong answer.) `limit` caps the number of *groups* on this path, and `group_limit`/`groups_truncated` say when that cap bound — the counts stay exact, only the ranking is cut. A `filter`/`filters` alongside `group_by` is forwarded only for a (view, field) pair measured to be accepted — `top-sources`/`srcip`, `top-destinations`/`dstip`, `policy-hits`/`policyid`, `top-countries`/`dstcountry`, `top-threats`/`threat` — and refused otherwise (`unsupported_view_filter`). A raw `filter` string never qualifies, whatever it contains, because its field names are not knowable here; pass `filters`. A dimension with no native surface at all is **refused** the same way, with a message naming `sample_by`: there is deliberately no fallback to sampling, because a top-N over a 1000-row sample reads as fact and gets quoted as fact. `sample_by=["<dim>", …]` is that bounded path, carrying the existing contract verbatim (`is_exact`, `analysis_mode`, `total_hits`, `total_hits_is_known`, `total_hit_source`, `observed_hits`, `slices_scanned`, `truncated_slices`, `log_limit_per_slice`, `recommendation`); it takes a list because one scan yields several independent breakdowns rather than a cross-tab, and `top_n=0` returns every bucket. `count_only=True` returns the total alone. Two of the three together is `conflicting_aggregation`; `fields` alongside any of them warns rather than errors, since it describes a row shape no rows will be returned in. Two **derived dimensions** — `port` (`"{proto}/{dstport}"`) and `icmp_type_code` — survive the consolidation as first-class dimensions: FortiAnalyzer does not populate `icmptype`/`icmpcode` but encodes the pair in `service`, and a FortiGate SD-WAN SLA probe tags an ICMP packet with the probed application's name, so anything that is not one of the two known encodings becomes `type=unknown` rather than inventing a type that never crossed the wire. `group_by` is wired for log queries only in this release — the dimension resolver also plans `alert`/`incident` group-bys onto a stats endpoint, and that resolution is unit-tested, but no tool parameter reaches it yet, so `get_alerts`/`get_incidents` group-by remains a follow-up.

### Changed
- **`search_devices` defaults to a curated projection (breaking against the just-released 2.11.0 default).** 2.11.0 shipped `search_devices` with `fields` defaulting to the full ~60-field device object. It now defaults to the curated device set and resolves English aliases against the `device` vocabulary (`serial_number` → `sn`). A name this server does not enumerate is **not** rejected: it is forwarded to dvmdb with a warning, so appliance fields never catalogued here (`oid`, `ha_mode`, `os_type`, `last_checked`) stay reachable. `fields=["*"]` restores the full object; dvmdb projection is native, so the untrimmed object never crosses the wire either way.
- **Three tool signatures changed while their request payloads were fixed (breaking; the payload defects are under Fixed).** `get_alert_incident_stats(stat_type=…)` → `(timescale=…)` ("month" | "hour"); `update_incident(assignee=…)` → `(last_user=…)`; `acknowledge_ioc_events(ioc_ids=[…], user=…)` → `(events=[{endpoint_id, source_ip, timestamp, comment}, …], comment=…)`. On the client layer `add_alert_comment` additionally sends `alertid` as an array (the tool still accepts one `alert_id`). No working call is lost: each old spelling was sending a parameter the appliance silently discarded or rejected, so nothing that worked before behaves differently — the names just now match what the endpoint reads.

### Removed
- **Thirteen tools consolidated into three (85 → 73).** Every removed tool's parameters are expressible on its replacement, so no capability is lost — but this is a **breaking change** to the tool surface. Migration:

### Fixed
- **`sample_by` on a composite-typed dimension leaked whole values (`masking/wrapper.py`).** `_mask_breakdowns` typed a bucket's `"value"` from `FIELD_TYPES` alone, but `url`, `referralurl`, `http_url`, `link` and `devvds` have no entry there — their flat keys are served by `COMPOSITE_URL_FULL`/`COMPOSITE_URL_HOST`/`COMPOSITE_DEVICE_VDOM`. An untyped dimension passes through by design, so `sample_by=["url"]` — an ordinary, warning-free call, since `url` is canonical in the webfilter, virus, attack and app-ctrl vocabularies — returned whole URLs in clear, in the same response as the token the same host carried under a flat key, with `hits` as the join key. The bucket value now goes through `_mask_entry` under the dimension's own name, so the rule the handler already documented holds literally: a bucket value gets exactly what the same value gets under a flat key of that name, reusing every composite handler unchanged. The `keep` check stays wrapped around the call, because `_mask_entry` does not consult the keep set on its typed-scalar path. A shape the handler cannot type — a non-dict bucket, or a non-list bucket container — now **burns** when the dimension is typed or composite, the fail-closed policy `_mask_target` and the URL-dict branch already follow; it failed open before. An untyped dimension keeps its passthrough. (Found in review of [#109](https://github.com/rstierli/fortianalyzer-mcp/pull/109); the `breakdowns` shape does not exist before this release, so this was a leak introduced here rather than an inherited one.)
- **dvmdb's device `name` defeated `FAZ_MASK_DEVICE_IDENTITY` (`masking/wrapper.py`).** `name` is the key dvmdb uses for a device and was in neither `FIELD_TYPES` nor `DEVICE_IDENTITY_TYPES`, so with the flag on a clear `name` sat beside its own `devname` token — the flag defeated rather than followed, the same shape as `devs` ([#79](https://github.com/rstierli/fortianalyzer-mcp/issues/79)) and `dev_name` ([#83](https://github.com/rstierli/fortianalyzer-mcp/issues/83)). Pre-existing, but this release makes it routine by putting `name` in the curated `_DEVICE_PROJECTION`. Not fixed with a blanket map entry: `name` is equally the ADOM key, the report-layout key and the device-group key, and measured with a blanket entry under the flag, an ADOM name tokenises (recoverable) while `"Monthly Security Report"` is not a valid hostname and **burns** to an irreversible placeholder, making `list_report_layouts` unusable. The record decides instead, as `incident_reporter` already does: a `name` is a device name only when a sibling proves the dict a device object (`sn`, `serialno`, `os_ver`, `os_type`, `platform_str`, `conn_status`, `dev_status`, `ha_mode`, `mr`, `patch`). Both halves are shape-scoped — pass 1 masks it under the flag, and the keep set collects it with the flag off, so the same name stays clear under `target[].value`.
- **`group_by` dispatched two dimensions to views that answer a different question (`query/groups.py`).** Live probing on 7.6.7 and 8.0.0 found `top-websites` returns rows keyed `catdesc`/`catid` with no hostname column at all, so `group_by="hostname"`/`"website"` reported web-category buckets under the caller's dimension name with `is_exact: true`; `top-applications` labels its rows `app_group`, so `group_by="app"` returned application groups. All three are removed from `LOG_GROUP_SURFACES` and now take the refusal path, which names `sample_by` — a real fallback, since `hostname` and `app` are genuine fields in their vocabularies. `catdesc` (aliases `web_category`, `category_description`) is mapped in their place, so the exact web-category surface is kept rather than lost.
- **The consolidation dropped every per-view sort default (`query/groups.py`, `tools/log_tools.py`, `skills/handlers.py`).** Each retired `get_top_*` wrapper hard-coded one — `bandwidth` for sources, destinations, applications and websites, `threatweight` for threats, `sessions` for cloud-applications, `counts` for policy-hits — and both replacements sent none, while responses still said "top N groups" and set `groups_truncated`: ranking claims about a sort never requested. One `VIEW_SORT_DEFAULTS` map now feeds the `group_by` dispatch and all eight migrated skill call sites; `get_fortiview_data` keeps `sort_by=None` in its own signature, since it is the generic passthrough. `docs/probes/2026-07-fortiview-surface.md` withheld these believing an unknown sort column would be silently ignored; measured, `sort_by='notacolumn'` returns a loud `Missing columns` error, so a wrong entry fails visibly and restoring is safe. `top-countries` is deliberately absent — no wrapper served it, so there is no measured default to restore.
- **Enum-valued filter fields accepted anything, silently (`query/fields.py`, `query/filters.py`).** The retired `search_*` wrappers validated their enum arguments client-side; the consolidation left `validate_traffic_action`, `validate_event_level` and `validate_event_subtype` with zero callers, and `compile_to_string` validates field names and operators but passes values through verbatim. Measured on 7.6.7 over one fixed hour: `action==deny` returned 5833 rows and `action==denied` returned **0, status success, no error** — a loud client-side rejection turned into a confident empty answer. `action`/`level`/`subtype` now carry known-member sets per vocabulary (traffic and attack disagree about `action`) and an unrecognised member **warns** rather than raising, matching how the same call path already treats an unrecognised field *name*: these sets are this server's knowledge, not the appliance's, and `VALID_TRAFFIC_ACTIONS` has six members where FortiGate emits others (`client-rst`, `server-rst`), so rejecting would make a real value unqueryable. Substring operators are exempt.
- **Breakdowns hid their own exclusions, and `total_hits` was not the floor it promised (`query/groups.py`, `tools/log_tools.py`).** Buckets silently dropped every row whose dimension value was absent or in `_ABSENT`, and a `top_n` cut was indistinguishable from "nothing else matched" — the retired policy tools reported this through `top_ports_residual`/`top_services_residual`/`top_applications_residual`, which the consolidation removed with no replacement. A new **`breakdown_residuals`** sibling key restores it on both producers: `{dimension: {excluded_rows, distinct_values, buckets_truncated, hits_shown, hits_total}}`, counts only, so nothing in it needs masking. It is a sibling rather than a richer bucket value on purpose — the masking handler types a bucket *list* by its dimension name and treats a non-list dimension value as a shape it cannot type, so enriching in place would have changed masking behaviour too. Separately, `query_logs` published `total_hits` straight from the appliance's total-count under a docstring promising a floor; it now clamps with `max(total, observed)` and logs when that fires, the shim `analyze_policy_traffic` has carried since v2.4.1.
- **One malformed `sample_by` dimension produced two different machine codes (`tools/traffic_tools.py`).** `analyze_policy_traffic` picked its code by sniffing the message for the word "field", and `resolve_field`'s shape rejection contains it, so the same input `query_logs` called `validation_error` came back as `unknown_field`. Decided structurally now, with no string sniffing. In the same loop, an alias and its canonical name are recognised as one dimension: `sample_by=["srcip", "source_ip"]` echoed two entries and scanned the rows twice while `breakdowns` collapsed to one key.
- **The argument unmasker resolved field-*name* arguments, reopening the token→plaintext oracle (`masking/fields.py`, `masking/unmask.py`).** `FIELD_NAME_ARGS` covered only `fields`, so `group_by`, `sample_by`, `sort_by` and `view_name` were resolved like values. Measured: `group_by='host-2a85-…'` came back as `secret-internal.corp.example`. It is worse than the `fields` case it repeats — `fields` needed a *valid* field name to reach `fields_returned`, whereas a token can never be a mapped dimension, so `group_by` always refuses and the refusal quotes the dimension back. Any token, one call, plaintext. All four now skip resolution: each names a field, a column or a view, never customer data, so there is nothing for unmasking to be right about. `sort_by`/`view_name` were the shipped instances of the same class and are closed here rather than left as the next one.
- **Aggregation breakdown buckets echoed their values unmasked (`masking/fields.py`, `masking/wrapper.py`).** `sample_by` returns `{dimension: [{"value": …, "hits": N}]}`, and neither masking pass reached that `"value"`: pass 1 masks a bare `value` key only when a sibling `type` key marks it a SOAR indicator, and pass 2 scans keys typed TEXT, which a generic `value` never is — a synthetic `{"breakdowns": {"srcip": [{"value": "10.1.2.3", …}]}}` survived whole. The dimension name sitting one level up now types each bucket, the same "the field decides the paired value's type" rule `groupby1` already uses. Dimensions whose values are prose (`msg`, `ui`, `subject`, `extrainfo`, `logdesc`, `prompt`) have no scalar type to mask by and are scanned in pass 2 instead, so a bucket value gets exactly what the same string gets under its own flat key — including resolution of a hostname this response masked elsewhere, which is otherwise the token-and-plaintext pairing the layer exists to withhold. Identifier-typed dimensions are deliberately left out of that second pass: a masked IPv4 is itself a valid IPv4, so scanning it twice would hand back a token matching nothing else in the response. A dimension with no type at all still passes through rather than being burned to a placeholder — `sample_by` accepts any field the rows carry, and most of them (`port`, `service`, `app`, `proto`) are not identifiers. (The prose half was found by Copilot's review of [#109](https://github.com/rstierli/fortianalyzer-mcp/pull/109).)
- **The aggregation paths dropped two deterministic advisories, and the group cap warning blamed the caller for them (`utils/responses.py`, `tools/log_tools.py`).** `build_warnings` is the rows-path builder, and two of its four conditions are not about rows: the `limit` clamp bounds a `group_by` ranking's top-N and a `sample_by` scan exactly as it bounds a page, and FAZ reads a naive window in its own timezone whatever the query returns. Only the rows path emitted them, so `query_logs(sample_by=["app"], limit=5000)` was answered from 1000 scanned rows with nothing saying so — the structured `log_limit_per_slice`/`group_limit` echoes were right all along, but a caller has to already suspect the clamp to go looking. Both messages are now single-sourced (`limit_clamped_warning`, `unknown_timezone_warning`) and emitted on `group_by`, `sample_by` and `count_only` as well, in the same order; the rows-path list is byte-identical. The other two conditions stay out deliberately: a bare count reports `total_is_known` structurally, and the high-volume advisory names `group_by`/`sample_by` as the remedy, which is absurd advice to someone already using them (a test now keeps it out). The truncation warning itself said "Returned the top 1000 groups, which is the cap `limit` set" to a caller who set 5000 — `limit` there is the *clamped* value — and then advised raising it to a maximum they had already exceeded; it now names the effective cap and only offers the raise when raising is actually the remedy.
- **FortiView received logview's all-devices token (`tools/fortiview_tools.py`).** `build_device_filter` speaks logview's dialect — every `All_*` group under `devid`, defaulting to `All_FortiGate` — while FortiView answers only to `[{"devname": "All_Device"}]` and answers the other spellings with an empty top-N and *no error*, which reads as "no traffic". `run_fortiview` and `get_fortiview_data` now translate every all-devices spelling through `build_fortiview_device_filter`; a named device and a serial are unchanged.
- **`VALID_LOG_TYPES` diverged from the appliance in both directions (`utils/validation.py`) — breaking: `utm` is now rejected.** Measured live on 7.6.6 (build 3654) via `/logview/logfields` with an unrecognised logtype, which returns the appliance's whole catalogue: there are 29 logtypes and all 29 start a real logsearch. Sixteen were rejected outright by local validation (`content`, `generic`, `history`, `im`, `sniffer`, `netscan`, `fct-event`, `fct-traffic`, `fct-netscan`, `waf`, `gtp`, `asset`, `protocol`, `siem`, `ztna`, `security`) and are now accepted. `utm` was accepted and is not a logtype at all — the appliance reads it as *no logtype filter* and starts an unscoped search wearing a scoped label — and is now a hard validation error naming the real catalogue. `anomaly`, `icap` and `virtual-patch` are appliance-side aliases resolving to `attack`, `protocol` and `security`; a new `LOG_TYPE_ALIASES` map resolves them explicitly so downstream sees one spelling per logtype. Indices 20–28 appear in neither the 7.6.6 nor the 8.0.0 FNDN documentation; the appliance is authoritative.
- **Four request payloads did not match the FNDN spec (`api/client.py`).** Found by diffing every `client.py` call site against the FNDN reference for 7.6.6 and 8.0.0; none were test-covered, because the suite mocks the client and FortiAnalyzer ignores unknown parameters rather than rejecting them, so each defect returned a normal-looking success. `add_alert_comment` sent the `add` verb where the spec documents `update` (live 7.6.6: "Invalid Request: Not supported method (add)" — the tool never worked) and a scalar `alertid` where the endpoint takes an array. `get_alert_incident_stats` sent a `type` parameter that does not exist on either version (live: a nonsense value and `"severity"` returned byte-identical responses); the endpoint takes `timescale` (month|hour), now exposed and validated. `acknowledge_ioc_events` sent `eventid` + `update-by`, neither of which occurs in the IOC spec — an IOC event has no standalone id, it is addressed by endpoint plus the timestamp it fired at, so the payload is an `events` array and the tool takes a typed `IocEventRef` list that rejects an event identifying neither endpoint nor source IP. `update_incident` sent `assignee`, which is not a field on this API (dropped silently while the call reported success); it maps to `lastuser`, the record's last-editor stamp. `tests/test_fndn_spec_conformance.py` pins each payload shape. Dynamic-mode dispatch, which only coerced `filters` into models, is generalised to `_coerce_model_list` over a `_structured_params` registry so the new `events` parameter (and the next typed list) survives dispatch instead of hitting an `AttributeError` buried in a generic error.
- **`time-range` on `/incidents` and `/incidents/count` is undocumented on 7.6.6 and 8.0.0 but measured to filter — the parameter stays.** Against a created incident, a window covering its createtime returns it, year-2000 and year-2099 windows return zero, and omitting the parameter returns it — identical to the documented `/incident/stats` control, reproduced end-to-end through the tool layer. Removing the parameter on the spec's word (which this branch briefly did) would have silently widened every incident query from the caller's window to ADOM-wide, truncated by `limit`; `tests/test_fndn_spec_conformance.py` now guards against re-attempting that. Second case on record of an FNDN omission not meaning the appliance ignores the field (logtypes 20–28 were the first); `docs/UPDATING.md` now states the method — measure before removing, with a well-formed window over an endpoint that has data, because FAZ degrades malformed values to the default silently and a wrong-shaped value 503s on documented and undocumented endpoints alike.

## [2.11.0] - 2026-08-05

### Added
- **Structured filters (`filters`) on `query_logs`, `search_devices` and `list_tasks`.** A list of `{field, op, value}` conditions compiled by one shared engine (`query/`) into whichever of FortiAnalyzer's *two* filter dialects the endpoint speaks — the string grammar for logview/fortiview/eventmgmt/incidentmgmt, the `[field, op, value]` array for dvmdb/config/task. Ops: `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `contains`, `not_contains`, `in`, `not_in`; conditions AND, and `in` becomes a parenthesised OR group. Because the parameter is a Pydantic model, FastMCP publishes the op enum in the tool schema, so an invalid operator is rejected at the protocol boundary rather than by the appliance. Field names resolve through a vocabulary registry that accepts unambiguous English aliases (`source_ip`, `destination_port`, `application`) and carries the enum coercions `search_devices` and `list_tasks` each held inline, so `conn_status` `"down"` means `2` everywhere. Unknown names are a hard error listing the valid set where the field set is enumerable (device, task) and a pass-through warning naming `get_log_fields` where it is not (logtypes, whose catalogues run to hundreds of entries the server does not reproduce); pass-through additionally requires the name to be *shaped* like a field name — the string dialect interpolates the resolved name, so a "field" carrying quotes, whitespace or operator characters is rejected as an injection attempt rather than handed the compiled filter string. The raw `filter` string remains, mutually exclusive with `filters`. Only operator spellings with working evidence against a live appliance are emitted: FortiAnalyzer documents more for its Log View parser, but nothing here exercises them through JSON-RPC, so they are reachable only via `filter` until a live check confirms them.
- **MCP tool annotations on every tool ([ADR 0003](docs/adr/0003-mcp-tool-annotations.md)).** All 89 declaration sites — 86 registered in full mode (85 raw tools + the `faz_skill` dispatcher) and the 3 dynamic-mode discovery tools — now declare `ToolAnnotations`, so a client can tell a reader from a writer instead of inheriting the spec defaults — which are `readOnlyHint=false`, `destructiveHint=true`, `idempotentHint=false`, meaning an unannotated `get_system_status` was advertising *"may modify its environment, possibly destructively"*. Six named categories in the new `tool_annotations` module (`READ_ONLY`, `READ_ONLY_LOCAL`, `CREATES`, `UPDATES`, `DESTRUCTIVE`, `UNCONSTRAINED`) set all four hint fields explicitly, including the two the spec calls meaningful only for writers: `destructiveHint` defaults to *true* on the wire, so omitting it on a reader misleads any client that reads the field without checking `readOnlyHint` first. The read-only line is FortiAnalyzer's stored state — the 14 tools that add, flip, replace or delete appliance state are the entire write surface; TID-creating queries (`query_logs`, `run_report`, `run_fortiview`) and local-file writers (`save_report`, the PCAP downloaders) stay read-only, the latter a documented trade-off in the ADR. `execute_advanced_tool` is annotated by reachability rather than by its own body, since `tool_name` selects any tool including `delete_device`. Advertisement only: no tool's behaviour changes, and annotations pass through the masking wrapper intact (verified with `MASKING_ENABLED=true`). 13 contract tests freeze the classification — a writer mis-annotated `READ_ONLY`, or a new tool registered with a bare `@mcp.tool()`, now fails the suite.
- **A server-level usage guide (`instructions=`), arbitrating the `tid` taxonomy.** `FastMCP` was constructed without `instructions`, so the only guidance a client ever saw was 86 individual docstrings — and a docstring cannot warn that a neighbouring tool spells something the same way and means something else. Five families return a value under `tid` and none are interchangeable: `query_logs` hands back a **reusable pagination handle** (an in-process registry key, not the appliance task id, which the appliance reaps after the first fetch), `run_fortiview` an int task id valid only when re-paired with the same `view_name`, `run_report` a **UUID string** rather than an int, `run_ioc_rescan` an int task id of a different job type, and `search_ips_logs` a vestigial echo of an already-reaped id that is not usable for anything. A caller generalizing "I hold a tid, so I can page it" from the first to any other gets failures whose cause appears in none of the docstrings it read. The new `instructions` module documents that table plus the filter grammar (`==`, `!=`, `<`, `>`, `<=`, `>=` and `like` with `%` wildcards, negated by wrapping the clause), the structured `filters` op vocabulary (including that `in` is rejected by the array-dialect tools `search_devices`/`list_tasks` — one call per value there), the three `time_range` vocabularies and which tools accept which, tool-selection guidance for the overlapping search/aggregation families, the `fields` escape hatch on `list_adoms`/`list_devices`, and an honest note that the error envelope is uniform only in the log-search and traffic families. 36 contract tests assert on tool names and operator tokens rather than prose, so the wording stays editable while a dropped tid family fails the suite.
- **`get_log_fields(name_filter=...)`.** The one tool meant to teach a caller what is filterable was a raw passthrough of roughly 200 definitions across two lists (a public list and a private-field list), making it cheaper to infer field names from a sample log row than to consult the catalogue. `name_filter` applies a case-insensitive substring match across *every* field list in the payload, and the response now carries `name_filter`, `field_count` and `total_field_count` so a narrowed answer is never mistaken for the whole catalogue. Filtering copies rather than editing the payload in place, non-field lists and scalar siblings pass through untouched, and a bare-list response (some FAZ endpoints answer without a wrapping dict) is handled — a shape change on the appliance degrades to a no-op instead of an exception. Default behaviour is unchanged: omitting `name_filter` still returns the full passthrough. The numeric `type` codes are left undocumented on purpose: 7.6.x returns `type` as a small integer (0, 4, 6, 10 and others observed) and publishes no legend for it — not in the Fortinet document library, and not in the `fortianalyzer-api-docs`/`-postman` references — so rather than invent a mapping the docstring marks the value opaque, passes it through unchanged, and directs callers to read the field in a sample `query_logs` row.

### Changed
- **The usage guide gains a masking section, shipped only when masking is on.** With `MASKING_ENABLED` the model receives format-preserving FPE tokens for identifiers and nothing told it they were tokens — so a token that reads as an odd hostname invites being "corrected", and an edited token resolves to nothing. `build_instructions(masking_enabled=...)` appends the section when the layer is installed and omits it otherwise, so a default deployment does not pay handshake tokens for advice about values it will never emit. The section names the operator to filter with, which is the non-obvious part: measured on live 7.6.6, dvmdb's `like` is **case-insensitive** (a lowercased device name still finds `DataCenterFw_FG200G`) while `==` is **case-sensitive** and returns `count: 0` with `status: "success"`, and the `get_device` object lookup fails loudly with `Object does not exist`. Since token alphabets are lowercase by design, a round-tripped device identifier survives `contains` and silently loses under `eq` — so the guidance is `op: "contains"`, not a generic warning about case.
- **The usage guide states that the narrow parameters AND with `filters`.** Both tool docstrings already said so; the server-level guide did not, and it is the guide a client reads before choosing a call. `name_filter`/`platform_filter`/`connection_status`/`filter_state` compose with structured conditions rather than being overridden by them, so two conditions on the same field must agree or nothing matches. Behaviour unchanged.
- **`search_devices` and `list_tasks` echo `filter_applied` and speak the standard error envelope.** Both now return the compiled filter entries they sent (or `null` when nothing narrowed the call), so a caller can verify what was queried instead of inferring it from which rows came back — `query_logs` already did this. Their validation failures (bad `connection_status`/`filter_state`, unknown field, refused op) and API failures now return the full `{status, error, message, operation, retry_count}` envelope instead of the bare `{status, message}` pair; existing keys are unchanged, so the upgrade is additive. `search_devices` also gains the `fields` projection `list_devices` always had (~60 fields per device otherwise), and its docstring now lists the accepted field-name aliases. The remaining tool modules still return the bare pair — the guide's "error shapes are not yet uniform" caveat still applies outside these two.
- **The usage guide's time_range claim matches per-tool reality.** The guide listed 7 preset tokens and said two forms work everywhere; the actual vocabulary is 14 presets for the log/FortiView/event/incident families, while the report tools accept only the hour/day subset (sub-hour presets are a hard error there) plus the appliance's `last-N-*` spelling. `list_adoms` documents the involuntary `oid` and the numeric `state` flag; `get_log_fields` states that `desc` mirrors `name`, so the catalogue names fields without describing them.
- **Cross-references between overlapping tools, in the docstrings.** Five tools can fetch traffic/security logs with different parameter surfaces and none said which to prefer. `query_logs` now names the narrower tool for each case it is commonly misused for; `search_traffic_logs` states that it wraps `query_logs` (so its `tid` *is* a working pagination handle) and points per-policy volume questions at `get_policy_traffic_profile`; `search_security_logs` and `search_ips_logs` delimit each other, and the latter warns that its `tid` is not pageable; `get_policy_traffic_profile` documents when to prefer it over raw row queries, names its two siblings, and restates the `is_exact`/`analysis_mode`/`total_hits_is_known` contract that callers must check before quoting numbers.
- **`list_adoms` and `list_devices` document the `fields` parameter they have always had.** Both default to every field the appliance defines — ~35 per ADOM and ~60 per device, most of them empty placeholders, plus credential keys returned as `***REDACTED***` — and the docstrings said only "returns all if not specified". Both now recommend a concrete projection. Response shapes are deliberately unchanged: flipping the default would break the field names callers already depend on. (A reviewer with live access concluded `list_devices` had no `fields` parameter at all, which is the cost this documents away.)

### Fixed
- **Array-dialect substring filtering never matched (`query/filters.py`, `dvm_tools`).** The dvmdb/task endpoints *accept* the documented `contain` spelling and silently match zero rows — probed live: `["name","contain","DataCen"]` returns nothing against a fleet where `["name","like","%DataCen%"]` returns the device. Every `search_devices` narrow parameter (`name_filter`, `platform_filter`, `os_version_filter`) and every structured `contains` on the array dialect was affected, returning empty results that read as "no such device". `contains` now compiles to `like` with `%` wildcards on both endpoints (caveat: `like` treats `%`/`_` as SQL wildcards, so a needle containing `_` can over-match by one character). `not_contains` is now refused on the array dialect with a remedy, because every candidate spelling (`!contain`, `not like`) also silently matches zero rows live — there is nothing correct to emit.
- **The string dialect's `contain` was inert in exactly the same way (`query/filters.py`, `instructions.py`, `log_tools`).** The logview parser accepts `contain`/`!contain` and matches nothing, so `contains` on `query_logs` — and `search_security_logs(attack_name=...)`, which hand-built `attack contain <name>` — answered "no such thing" with total confidence. The parser does not reject operators it does not know: a nonsense `service zzqq DNS` behaves identically, which is what distinguishes an inert operator from a strict one. Measured independently on 7.6.6, 7.6.7 and 8.0.0; on 7.6.6 over one fixed hour of traffic (289391 rows): `service==DNS` 120618, `service like "%DNS%"` 120671, `!(service like "%DNS%")` 168720, `service contain DNS` **0**, `service !contain DNS` **0**. The two `like` figures sum to the window total exactly, so the wrapped negation is a true complement rather than a match-everything. Both ops now compile to `like` with `%` wildcards, negation wrapping the whole clause — `not like`, `!like` and `nlike` are each rejected live with `Invalid filter`, so wrapping is the only working form. The wildcards are sanitised together with the value, so the pattern stays one escaped literal and cannot terminate its own clause. The usage guide and the `query_logs` docstring no longer advertise `contain` to the model, and warn that a hand-written one fails silently. (Reported and fixed by @inxbit.)
- **`contains` over a field stored as an enum code compiled to a wildcard over the integer (`query/filters.py`).** `coerce_value` runs before the wildcards attach, so `{"field": "state", "op": "contains", "value": "running"}` became `[["state", "like", "%1%"]]` — confirmed live in `list_tasks`' own `filter_applied` echo — and `TASK_STATE_CODES` runs 0..10, so `%1%` matched state 1 (running) *and* state 10 (unknown), while `%0%` matched 0 (pending) and 10. `conn_status` escaped notice only because its codes are 0/1/2. Substring ops on such a field are now refused on both dialects, listing the accepted enum names, because the stored value is an integer and the caller asked for a substring of a name: there is nothing correct to emit. Substring matching on free-text fields is unaffected.
- **A boolean inside a filter value list was silently accepted (`query/filters.py`).** `{"dstport", "eq", true}` correctly errored while `{"dstport", "in", [true, false]}` compiled to `(dstport==1 or dstport==0)`, an invented port filter, because the list arm was typed `list[str | int]` and pydantic coerced the bool to an int before the boolean guard could see it — that guard was dead on every validated path. `bool` now appears in the list arm, so both shapes fail identically. (Reported and fixed by @inxbit.)
- **`sanitize_filter_value` accepted control characters (`utils/validation.py`).** A raw newline, NUL or ESC inside a value was escaped, quoted and shipped; FortiAnalyzer then rejected the *entire* expression with `Invalid filter` (verified live on 7.6.6: `service=="DN\nS"` errors where the same filter without the newline returns rows). Not an injection vector — a quoted control character cannot terminate its clause — but it failed at the appliance after a round trip rather than at the protocol boundary, which is the pattern this layer exists to remove. Control characters are now refused up front and the error names the field, matching `validate_pcapurl` in the same module. Surrounding whitespace is still stripped rather than refused.
- **`get_log_fields` filtering and counts never reached the live payload (`log_tools`).** Live 7.6.x nests the field lists inside a wrapper object — `data[0].field` and `data[0]["private-field"]` — whose keys carry no `name`, and the payload walk only inspected a list's direct entries, so the whole catalogue counted as zero and `name_filter` passed everything through untouched (measured live: 234 + 26 traffic fields, `field_count: 0`). The walk now recurses into list elements; the flat shapes remain covered, and the docstring's navigation example now shows the real nesting.
- **Masked values inside structured filter conditions are resolved (`masking/unmask.py`).** `unmask_args` types a value by its own key and `unmask_filter` types it by the field name preceding it in the expression; a `{field, op, value}` condition does neither, since the value sits under the literal key `value` while its field name is a sibling — and a Pydantic model instance, which is what FastMCP passes for a `list[FilterCondition]` parameter, was not walked at all. Measured on the previous code, `unmask_args({"field": "srcip", "op": "eq", "value": <masked ip>})` returned the token untouched. Because a masked IP is format-preserving and unmarked, a masking-enabled deployment would have sent a valid-but-different address to the appliance and received real logs for a host nobody asked about — a confident wrong answer rather than an empty result. Conditions are now typed by their sibling field in both dict and model form, and the sibling field is canonicalised through the query alias table first — the compilers accept `source_ip` for `srcip` and the usage guide advertises that, so typed by the raw alias spelling an unmarked IP token would have slipped through untouched.
- **One filter-value sanitiser (`traffic_tools`).** The module carried a second `sanitize_filter_value` whose safe-character class omitted `:`, so it quoted every IPv6 literal while `utils.validation` left it bare — the same value spelled two ways depending on which tool built the filter.
- **Resolved address-object labels (`srcuuid_name`/`dstuuid_name`) leaked verbatim (`masking/fields.py`).** Populated on ~90% of live traffic rows, these names rode through in clear. They now type as `TEXT` rather than `HOSTNAME`, so free-form labels (spaces, punctuation) never burn to an irreversible placeholder while embedded IOCs still mask in place; the raw `srcuuid`/`dstuuid` stay clear (no human content). Documented residual (#80): a plain descriptive label carrying no embedded IOC rides through clear on both the inbound and outbound halves. (#101, residual recorded in #105.)
- **Composite-shape and target-entry fail-open residuals (`masking/unmask.py`, `masking/wrapper.py`) — #73 items 1–3.** Composite keys (`groupby1`/`groupby2`, `url`/`http_url`) arriving in an unexpected list or dict shape fell through their type-guarded branches to the allowlist walk, which cannot type a bare string element, and leaked. List elements now mask through the prefixed / host-only handlers; a dict under a URL key has no slot the handlers can type, so it burns whole (fail-closed, matching the #71 non-list policy). A `target` entry carrying neither `name` nor `value` parked its identifier in the entry's own dict key, which the rebuild loop copied through in clear; such an entry now burns whole. Pinning tests hold both boundaries so the burn cannot creep. (#104.)
- **Filter-clause field group was not anchored, so a fragment could hijack a clause (`masking/unmask.py`) — #73 item 7a.** The clause regex let the field group start mid-word, so a non-clause fragment like `a-srcip=<ip>` inside a filter string read as a `srcip` clause and the address was silently transformed to a different one. A word-boundary lookbehind closes it for every operator at once. Documented cost: a dotted spelling (`foo.srcip`) no longer resolves as `srcip` — priced at zero, since on live 7.6.7 and 8.0.0 a dotted field spelling matches zero rows while the plain spelling matches thousands in the same window. Two residuals of the anchor (extra-separator bypass; `host-`/`user-` prefix false-refusal) are tracked as #73 7b/7c. (#107.)

### Security
- **Masking token restoration is gated on the read-only annotation (`masking/unmask.py`, `masking/wrapper.py`).** `unmask_args` ran on *every* wrapped tool, so a masking token supplied as an argument to a mutating tool was decrypted and written into the estate — and FF3 tokens carry no integrity tag, so a stale or forged token under the current key decrypts to some plausible value that could be written with no error raised. Restoration now runs only for tools that annotate themselves read-only; everything else — an unannotated tool, and the dynamic dispatcher whose annotation is deliberately the union of everything it can reach — fails closed: arguments pass through unrestored, and a whole-value marked token is refused with an error envelope that names the argument and never echoes the token. A token embedded in a longer string passes through as token text (it discloses nothing). Unmarked IP and MAC tokens remain indistinguishable from real addresses and still pass through. (Builds on this release's tool annotations; fixes #106 via #108.)

### Fixed

- **Free-text masking handles re-cased identifiers without conflating case-sensitive principals.** Hostname and domain echoes now match case-insensitively in one pass, exact username spelling retains its own reversible token, and substituted tokens are not rescanned (previously a token containing the pad character could be corrupted by a later pass, which lost the value). Case folding is ASCII-only, so an identifier is matched across ordinary upper/lower/title spellings but a lookalike that merely case-folds into it under full Unicode rules is left alone rather than being rewritten or burned. When two principals in the same response differ only in case, a third spelling belongs to neither and now fails closed to a placeholder instead of being attributed to whichever was seen first. Substitution compiles one alternation per text field instead of one regex per known value, which removes a cache cliff that made large result sets disproportionately slow; peak memory grows with the number of distinct identifiers in a response (roughly 2 KB each). Note the widened matching also rewrites ordinary prose words that happen to equal a masked identifier in another case, so an estate with usernames like `backup` or `system` will see those words tokenized in log prose.
- **Masked filter values resolve under the FAZ operators this project accepts.** Single `=`, `!~`, `~`, and spaced `!contain` clauses now resolve through the same quoting and filter-injection defenses as the existing operators.

### Added
- **`threat`/`obf_url` (fortiview `top-threats`) are masked as a domain pair, closing the browsed-destination leak.** A non-empty `obf_url` marks the row: it is populated exactly when `threat` holds a browsable web domain (as its `[dot]`-escaped twin) and empty on every signature, filename and anomaly row, verified across both reference estates on the RFC [#40](https://github.com/rstierli/fortianalyzer-mcp/issues/40) thread (`logtype` does not discriminate, and malware rows carry dotted filenames any shape test would misread). With `obf_url` set, `threat` masks as a domain and `obf_url` is unescaped, masked and re-escaped so the pair stays consistent; with it empty, `threat` keeps its analytic value. Documented fail-open residual: a build emitting a domain `threat` with an empty `obf_url` would leak that row class; the leak test carries a tripwire assertion so a counterexample fails a test instead of leaking silently.
- **Tool-argument unmasking — Phase 2 of RFC [#40](https://github.com/rstierli/fortianalyzer-mcp/issues/40).** With masking on, masked tokens the model hands back as tool arguments are resolved to real values BEFORE input validators and the FAZ API see them: marked tokens (`host-`/`user-` prefixes, domain/email suffix forms) resolve anywhere — bare arguments, list items, nested dicts (e.g. a dispatcher's `params` object), and inside filter-expression clauses — while unmarked IP/MAC tokens resolve only where the argument or filter field name identifies the type. Failure policy: a marked token that does not decrypt is passed through so the downstream validator rejects it loudly (incl. rotated-key tokens, which log the key-id mismatch); an unmarked non-decrypting value passes through as a probably-real address. Documented residual: deterministic FPE cannot distinguish a real IP typed by an operator from a token of the same shape.
- **Tool-output masking (`MASKING_ENABLED`, default off) — Phase 1 of RFC [#40](https://github.com/rstierli/fortianalyzer-mcp/issues/40).** With the flag on (requires `FAZ_MASKING_KEY`), every registered tool's result is masked before it reaches the LLM: allowlisted fields are masked by type at any nesting depth (including composite keys such as `groupby1`/`grpby`/`target`/`devvds`), then free text (`msg`, `logdesc`, echoed `filter` strings, ...) gets an IOC scan plus substitution of every value masked elsewhere in the same response. Fail-closed: unmaskable values become irreversible keyed placeholders, and a masking failure withholds the raw result behind a `masking_failed` error envelope. Device identity (`devname`, `devid`, `sn`, ...) is masked only with the separate `FAZ_MASK_DEVICE_IDENTITY` flag.
- **FPE masking engine (`fortianalyzer_mcp.masking`) — Phase 0 of the reversible data-masking RFC [#40](https://github.com/rstierli/fortianalyzer-mcp/issues/40).** Format-preserving encryption (NIST FF3-1 via the `ff3` package) with per-type deterministic, key-reversible mask/unmask for IPv4/IPv6, MAC, hostname, username, domain, and email values. Tokens carry recognizable markers where reversibility allows (`host-`/`user-` prefixes, `.masked.invalid` suffix for domains/emails), and every marked token embeds a 4-hex-char one-way key id so a token minted under a rotated key fails loudly on unmask instead of decrypting to a plausible wrong value (IP/MAC tokens cannot carry one — documented residual). Usernames use a mixed-case FF3 alphabet and round-trip case-preserved (`Admin` and `admin` are distinct principals); the other string types normalize to lowercase. Short values are padded to satisfy the FF3-1 minimum domain size and over-length values are chunked with position-varied tweaks. Two RFC deviations found during verification are documented in the module: fully reversible MAC and email tokens cannot keep a fixed reserved OUI / replacement domain, so MACs share the RFC's "IP wrinkle".

- **`MCP_ALLOWED_HOSTS` no longer crashes startup when set in the documented comma-separated format.** pydantic-settings JSON-decodes `list[str]` env fields, so `MCP_ALLOWED_HOSTS=faz.example.com,proxy.internal` (or even a single host) raised `SettingsError` before the server started. The field is now annotated `NoDecode` with a before-validator that accepts a comma-separated string or a JSON array. Requires pydantic-settings >= 2.3.0 (floor bumped in `pyproject.toml`).
- **`wait_for_task` / `list_tasks(filter_state=...)` handle the numeric task `state` FAZ actually returns.** `/task/task` reports `state` as an int (done=4, error=5, ...); `wait_for_task` called `.lower()` on it (AttributeError on every poll) and `list_tasks` compared the string name against the numeric field (silently empty). Both now normalize via a shared state-code map; string states keep working, and unknown `filter_state` values are rejected instead of matching nothing.
- **`build_device_filter` no longer misroutes hostnames that start with a serial prefix.** Names like `FGT-HQ-01`/`FG-BRANCH` were sent as `devid`, making every log/traffic/pcap search for that device silently return zero rows. The devid branch now requires a full serial match, including a new VM-serial form (`FMG-VM...`, `FAZ-VMTM...`).
- **FortiView tools route the device filter through `build_device_filter`.** `run_fortiview`/`get_fortiview_data` sent everything (including serials) as `devname`, silently scoping the query to nothing for serial input. The `All_Device` default is preserved.
- **Reports: custom `"start|end"` time ranges no longer silently cover the wrong period.** Previously `run_report`/`run_and_wait_report` sent `time-period: "other"` with no window, so FAZ ran the report over the layout's default period (verified live on 7.6.7 and 8.0.0). Now: `run_and_wait_report` configures the window on the layout's schedule config object (`update /config/adom/{adom}/sql-report/schedule/{layout_id}`: numeric `time-period` 16 = "other" + `period-start`/`period-end` in FortiOS timedate `"HH:MM yyyy/mm/dd"`, the format FAZ verifiably parses), verifies it by read-back (an unaccepted window aborts the run with an error), HOLDS it until generation completes — FAZ reads the schedule at generation time, not submission (verified live) — then restores the previous period. The success payload echoes `requested_window`, checks the shared schedule wasn't changed mid-run, and carries an explicit warning until generator consumption of the stored window is confirmed live (`tools/verify_custom_window.py --phase mech` discriminates the remaining run-mechanism hypotheses). `run_report` (fire-and-forget) rejects custom ranges outright, since it cannot hold the shared schedule through generation. Unknown presets (e.g. `"14-day"`) raise a validation error instead of silently becoming `last-7-days`, and the report device filter uses `build_device_filter` instead of hardcoding `devid`.
- **Progress percentages returned as strings no longer break polling.** `get_fortiview_data`, `fetch_fortiview`, and the `run_and_wait_report` wait loop coerce `percentage`/`percent` numerically (shared `coerce_num`, moved from `log_tools` to `utils.responses`) instead of comparing `"50" >= 100` (TypeError swallowed into a generic error).
- **Transient-error retries no longer replay non-idempotent writes.** A network error after FAZ accepted an ADD/SET/EXEC (e.g. `create_incident`, `add_device`) could double-execute it on retry. Transient retry is now gated to GET requests; the reconnect-once path for expired sessions stays enabled for all verbs (an expired session means the request never executed).
- **`run_fortiview` / `run_ioc_rescan` return an error when FAZ supplies no TID** instead of a success payload with `tid: null` that fails on the next call.
- **`fetch_fortiview` reports completion state** (`complete`, `percentage`, warning) so a fetch before the scan reaches 100% is no longer indistinguishable from final results (partial top-N).
- **`search_ips_logs` no longer fabricates `total` when FAZ omits the match count.** It reports `total: null` + `total_is_known: false` + a truncation warning instead of `total = len(logs)`, which made a limit-capped page look like an exact count.
- **`search_traffic_logs(policy_id=0)` now filters on the implicit-deny policy** (`if policy_id:` dropped id 0).
- **`search_devices(connection_status=...)` uses the DVMDB enum** (unknown=0, up=1, down=2) and rejects unrecognized values; `"down"` previously matched *unknown* devices.
- **`get_system_timezone` caches a definitive negative result**, eliminating one extra `/sys/status` round-trip per relative-range query on FAZ builds that don't report a parseable timezone. Probe failures (FAZ unreachable) are not cached.
- **List-form JSON-RPC results with a string `status` no longer crash `_raw_request_once`** (`AttributeError` on `"ok".get(...)`); string statuses are tolerated the same way the dict-form branch already did.
- **Repeated failed `connect()` calls no longer leak a `requests.Session` per attempt** (the half-built pyfmg instance is cleared on failure).
- **docker-compose healthcheck works again**: it invoked `curl`, which `python:3.12-slim` does not ship, overriding the image's working python healthcheck and marking the container permanently unhealthy.

## [2.0.1] - 2026-06-09

Reliability hardening for FortiAnalyzer 7.6.7. PR [#18](https://github.com/rstierli/fortianalyzer-mcp/pull/18) by [@inxbit](https://github.com/inxbit). 529 unit tests pass; live-verified end-to-end on a 7.6.7 appliance.

### Fixed
- **Log search no longer drains the appliance search-slot pool on FortiAnalyzer 7.6.7.** The shared page runner used to call `logsearch_fetch` immediately after `logsearch_start`, before the async search had finished. On 7.6.7 that premature fetch returned an incomplete page **and reaped the single-use tid**, so the runner re-issued a fresh `logsearch_start` ~once/second for 60s — no search ever completed, and the ~60 starts drained the appliance's search-slot pool (`query_logs` / `fetch_more_logs` / bounded policy slices / PCAP searches all returned zero rows / `search_timeout` / `No available slot for searching`). Replaced with a shared `_run_logsearch_page` whose contract is **poll-before-fetch**: `ensure_connected → logsearch_start → poll logsearch_count` (a cheap GET that does NOT reap the tid) until the scan is complete, then `logsearch_fetch` exactly once. Readiness is `progress-percent >= 100` OR (`total-logs > 0` AND `scanned-logs >= total-logs`) — `matched-logs` is deliberately not a readiness signal.
- **Server lifecycle no longer disconnects the shared client around every HTTP request.** `FastMCP(lifespan=...)` with `stateless_http=True` runs the lifespan per request/session, so the global `faz_client` was being connected then disconnected around every call, dropping the session out from under concurrent requests. Lifecycle ownership moved to `run_http`'s `app_lifespan` (Starlette-level) and `run_stdio`'s coroutine — a single owner for the server's lifetime.
- **Concurrent reconnects no longer race to tear down a revived session.** `_force_reconnect` is now serialized by an `asyncio.Lock` with a generation counter — when several concurrent requests all hit a dropped session, only the first re-logs in; the others observe the bumped generation and return without clearing the revived `_fmg`.
- **Relative time-range windows no longer silently miss recent logs after an upgrade.** FAZ interprets the naive `time-range` timestamps a logview search sends against its LogView ingest clock, which can drift from system "now" — notably after a version upgrade — so a relative window like `"1-hour"` anchored on system-now could land *ahead* of the newest ingested log and return zero rows even though traffic exists. Relative windows are now anchored on the appliance's LogView clock via a probe chain (`logfiles_state → logstats → faz_tz → naive`), with ±2-day / +400-day plausibility guards. Custom absolute ranges (`"start|end"`) skip the probe.

### Added
- **Bounded concurrent in-flight searches across every call site in this process.** A global `asyncio.Semaphore(LOGSEARCH_CONCURRENCY_LIMIT=4)` wraps the page runner, so `query_logs`, `fetch_more_logs`, the policy fan-out, and PCAP searches share one cap. Because a search now **holds** a slot for its whole budget (poll-before-fetch), the appliance-slot guard lives at the shared runner rather than only in the policy fan-out.
- **Shared bounded recovery budget across all reissue causes.** A single `MAX_SEARCH_REISSUES=3` budget covers invalid-tid during count, the invalid-tid race during fetch, and the "premature 100%" empty page — so a reaping appliance can spin at most `1 + MAX_SEARCH_REISSUES = 4` starts per page and is bounded by the wall-clock deadline as well. No new start or fetch is issued past the deadline.
- **Bounded `logsearch_count` and `logsearch_fetch` awaits.** Both calls are wrapped in `asyncio.wait_for` against the remaining wall-clock budget, so a stuck count/fetch cannot extend the slot hold past the search's own timeout.
- **Shielded best-effort cleanup-cancel on non-delivered exits.** Any path that leaves a started search un-fetched (count/fetch error, cancellation, deadline) issues a `logsearch_cancel` under `asyncio.shield(asyncio.wait_for(..., 2.0))` so a cancelled request still dispatches the cancel before the `CancelledError` propagates. If even the dispatch cannot run, the appliance reaps the single-use task on its own.
- **`MAX_SEARCH_TIMEOUT = 300s` upper bound on a single search's wall-clock budget.** Prevents a caller passing a huge timeout from monopolizing a concurrency slot.
- **Fallback for older builds without `logsearch/count`.** A clear unsupported-endpoint error (e.g. `Unknown URL`) falls back to a single direct fetch on the same tid and caches the per-client flag so subsequent searches skip the count probe entirely. Invalid-tid and timeout errors deliberately do NOT trigger the fallback.
- **`time_basis_source` and `clock_skew_seconds` on log-query responses.** Surfaces the LogView clock detection outcome (`logfiles_state` / `logstats` / `faz_tz` / `naive`) so callers can audit which clock anchored the window and by how much it skewed from FAZ "now".
- **`tests/test_logsearch_runner.py`** (646 lines): regression coverage that makes the fakes raise invalid-tid on fetch-before-complete, so the "exactly one start" assertions would fail against the old fetch-first runner. Pins the no-slot-exhaustion contract, the shared-budget cap, deadline behavior across 5 separate branches, leak cleanup, concurrency-cap saturation, and the count-unsupported fallback.

### Security
- **Defense-in-depth path-traversal guard on the report raw-save branch.** `save_report` now asserts the resolved output file stays within the validated output directory, mirroring the ZIP-extract guard added in 1.3.0.

## [2.0.0] - 2026-06-09

Breaking change: policy `estimated_total_hits` / `estimate_available` removed in favor of authoritative `total_hits` + `total_hits_is_known` + `total_hit_source`. See **Changed** section. PR [#17](https://github.com/rstierli/fortianalyzer-mcp/pull/17) by [@inxbit](https://github.com/inxbit).

### Fixed
- **`fetch_more_logs` no longer fails with "Invalid tid".** A FortiAnalyzer logsearch task id is single-use — the first fetch delivers the requested `offset`/`limit` slice plus `total-count`, and the appliance then reaps the task, so any second fetch on the same tid returns `Invalid tid` regardless of ADOM (verified on a live FAZ 7.4.x appliance). `fetch_more_logs` now reconstructs and re-runs the original query (same ADOM, logtype, filter, device, and absolute time window) at the requested offset, which the appliance returns in a stable order, so paging is correct and consistent. An unknown/expired pagination handle returns a structured `error="tid_invalid_or_expired"` error with a recommendation to re-run `query_logs`.
- **`total` is now accurate.** `query_logs` previously read a non-existent `total-lines` key (so `total` always equalled the page `count`); it now reads `total-count` from the fetch response and reports `total_is_known=false` when unavailable.
- **FAZ timezone detection across builds.** `get_system_timezone()` now reads the IANA name from either the `TZ` or `Time Zone` field of `/sys/status`.
- **Reliable bounded policy queries on slow searches.** The policy traffic tools now re-issue a fresh search per slice instead of re-fetching a single-use FortiAnalyzer `tid` (the same single-use-tid model as `query_logs`). Previously, if a slice — or the new whole-window total-count, most likely on large 7/30-day windows — returned incomplete on the first fetch, the next poll hit a reaped tid and failed that policy with `policy_query_failed`. Re-issues are bounded by the existing wall-clock timeout.

### Added
- **Reusable pagination handle + richer `query_logs` output.** `query_logs` returns `tid` (a reusable pagination handle), `has_more`, `next_offset`, `total`, `total_is_known`, `warnings`, `timezone`, `time_basis`, the resolved `time_range`, and echoes `adom`/`logtype`/`filter`/`device`/`offset`/`limit` for auditability. `fetch_more_logs` returns the same self-describing shape.
- **Automatic reconnect-once.** Log tools call `FortiAnalyzerClient.ensure_connected()` before issuing requests, so an idle-closed session is transparently revived instead of surfacing a raw "Not connected. Call connect() first." error.
- **Bounded transient retry.** Client requests retry transient FAZ/network errors (internal error, task timeout, network) with exponential backoff; validation and invalid-tid errors are never retried.
- **`cancel_log_search`** now releases the in-process pagination handle (the appliance task is usually already reaped, so the appliance-side cancel is best-effort).
- **One structured error envelope.** Every tool error path returns `{status:"error", error:<machine code>, message, operation, retry_count}` (plus `adom`/`logtype`/`tid` where relevant). Codes: `validation_error`, `invalid_time_range`, `invalid_tid`, `tid_invalid_or_expired`, `search_timeout`, `network_error`, `faz_operation_failed`; `retry_count` is the number of transient request retries the client performed.
- **`warnings` + `next_offset` on log queries.** `query_logs`/`fetch_more_logs` include a `warnings` list (clamped `limit`, unknown `total`, undetected timezone, or a high-volume result set that points to the bounded policy tools) and a `next_offset` to drive the next page.
- **Policy-tool audit metadata.** `get_policy_traffic_profile`/`get_policy_port_analysis`/`get_policy_protocol_summary` now return top-level `adom`, resolved `time_range`, and `timezone`, plus a per-policy `filter`; the analysis window is resolved once and shared by the bounded slices and the whole-window total-count query.
- **Authoritative policy `total_hits`.** The three policy tools now report `total_hits` from a whole-window FortiAnalyzer log-search `total-count` for the same policy/action/device/time filter, with `total_hits_is_known` and `total_hit_source` (`"logsearch_total-count"` when authoritative, `"observed_rows"` when it fell back to fetched rows). The port/protocol/service/application breakdowns and residuals still describe observed rows only. The total-count is best-effort: if it fails, the per-policy observations are still returned with `total_hit_source="observed_rows"`.
- **Custom time-range validation.** A custom `"start|end"` range is validated for `YYYY-MM-DD HH:MM:SS` format and `start <= end`, returning a clear `invalid_time_range` error instead of failing deep in slicing.

### Changed
- A completed logsearch task discovered reaped mid-poll is re-issued (bounded) so a slow search that finishes between polls still returns its results instead of failing.
- Response fields were finalized before release: `total_known` → `total_is_known`, `returned_offset`/`returned_limit` → `offset`/`limit`, and the error key `error_type` → `error` (a stable machine code). These only ever existed in pre-release builds.
- **Policy `estimated_total_hits`/`estimate_available` removed.** The optional best-effort FortiView `policy-hits` estimate (shipped through 1.3.0) is replaced by the authoritative whole-window `total_hits` above. Consumers that read `estimated_total_hits`/`estimate_available` should switch to `total_hits` + `total_hits_is_known` + `total_hit_source`.
- **`is_exact`/`analysis_mode` honest about partial breakdowns.** A policy result is `is_exact=true`/`"complete"` only when no slice was truncated **and** `total_hits == observed_hits`; when the authoritative total exceeds the observed rows the result is `"bounded_sample"` with the narrow-the-window recommendation, so a partial breakdown is never labelled complete.

### Security
- **Secret redaction in errors and logs.** Tool error messages and the logged search filter pass through a redaction-then-truncation helper, so tokens/session ids are masked and oversized internal errors are bounded before reaching a response or log. The raw `filter=` argument on `query_logs` is documented as a caller-controlled expert escape hatch (the `search_*` helpers remain validated/sanitized).

## [1.3.0] - 2026-05-29

First stable release — graduated from beta.

### Security
- **Log-query filter injection fixed** ([#16](https://github.com/rstierli/fortianalyzer-mcp/issues/16)): caller-supplied filter fields in the IPS/PCAP and traffic/security/event log search tools (`srcip`, `dstip`, `srcport`, `dstport`, `severity`, `action`, `level`, `subtype`, `cve`, `attack_name`, `session_id`) are now validated/sanitized before being interpolated into FAZ filter expressions. Filter operators and quoting are unchanged, so legitimate queries behave identically.
- **PCAP-by-URL validation** ([#16](https://github.com/rstierli/fortianalyzer-mcp/issues/16)): `download_pcap_by_url` / `get_pcap_file` now validate that `pcapurl` is an internal FAZ resource reference and reject arbitrary external URL schemes before forwarding to FortiAnalyzer.
- **Archive-extraction path containment** ([#16](https://github.com/rstierli/fortianalyzer-mcp/issues/16)): PCAP and report ZIP extraction now asserts each resolved path stays within the intended output directory (defense-in-depth on top of the existing basename handling).

### Changed
- **Stability promotion:** no functional changes beyond the security hardening above. Shipped example configs (`docker-compose.yml`, `.env.example`) and README now default to `FORTIANALYZER_VERIFY_SSL=true` with CA-import guidance, document a strong `MCP_AUTH_TOKEN` for HTTP mode, and warn that running HTTP transport without a token leaves all tools unauthenticated. ## [1.2.1-beta] - 2026-05-17

### Fixed
- **Relative time-range queries no longer silently miss logs when client and FAZ have different system timezones** ([#13](https://github.com/rstierli/fortianalyzer-mcp/issues/13)). FAZ accepts naive `YYYY-MM-DD HH:MM:SS` timestamps and interprets them in its own system TZ. The MCP previously called `datetime.now()` (caller-local) and formatted naive, so when client and FAZ disagreed by N hours every relative window smaller than N silently returned zero logs. Discovered with a fresh FAZ 8.0.0 GA defaulting to US/Pacific while the client lived in CEST — `search_traffic_logs(time_range="1-hour")` was searching a window 9 hours in the future. The MCP now reads FAZ's IANA TZ from `get_system_status`, caches it on the client, and computes "now" in UTC → FAZ-local before formatting. Custom absolute ranges (`"start|end"`) skip the TZ lookup.
- **Unknown `time_range` keys now raise `ValueError` instead of silently falling back to 1-hour or 24-hour.** Typos like `"30-min"` or `"5-min"` no longer produce wrong-but-plausible windows.

### Added
- **More relative-range presets supported uniformly across all tools:** `now / 5-min / 15-min / 30-min / 1-hour / 2-hour / 6-hour / 12-hour / 24-hour / 1-day / 2-day / 7-day / 30-day / 90-day`. Previously each of the 8 tool files supported a slightly different subset.
- **FortiAnalyzer 8.0.x support** — tested against 8.0.0 GA (build 0105).
- **`FortiAnalyzerClient.get_system_timezone()`** — public async method that returns the cached FAZ IANA timezone as a `zoneinfo.ZoneInfo`.

### Changed
- **Consolidated 8 duplicate `_parse_time_range` implementations** into a single `utils/time_range.py` (single source of truth). Each tool now uses a thin async wrapper that delegates to the shared utility with the FAZ-cached TZ.
